# Mode 2 扫描的 kill -9 断点续跑（resume journal）— 设计

日期: 2026-11-05
状态: 待评审（v2：全文语言重写，技术内容与 v1 相同）

## 1. 背景与动机

客户桶的规模：几十亿个对象、几到几十 TB。目录分布不均匀且事先不知道，没法预先切分成小任务，所以扫描是"整个桶一轮跑完"，最大的目录可能要跑一个星期。

一轮全扫的时长 ≈ 对象数 × 每对象探测请求数 ÷ 系统 read IOPS。按 IOPS=5000 算：20 亿对象约 9 天，50 亿约 23 天。

进程跑这么久，被 kill -9（或 OOM、机器重启）是迟早的事。而现在的设计里 kill -9 是唯一丢进度的路径（AGENTS §4.20）：什么都没记下来，只能从头重扫。对长跑来说这等于跑不完——按每天 5% 的概率被 kill 算，一个 23 天的任务平均要尝试 3 次以上才能有一次完整跑完。

优雅停机（SIGINT/SIGTERM）已经是完备断点：第一次信号会把"正在列举的页的游标、还没开始的前缀"写进 list_failed.txt，下次用 -resume-list 接着跑。kill -9 的问题是：没有任何代码有机会执行，什么都写不下来。

本设计一句话：**把"中断现场"从"收到信号时一次性写"改成"每 10 分钟持续写"。**写进一个 journal 文件，恢复时重放它，从上次写盘的进度继续。

## 2. 目标 / 非目标

**目标**：

1. kill -9 后，Mode 2 扫描从上次写盘点继续。损失的工作量 ≤ 10 分钟（约占整轮 0.01%）。
2. 恢复时不重新列举任何已完成的部分（目录树结构记在 journal 里）。
3. 记账的最小单位是"一页 LIST 结果"（约 1000 个对象记一行），不逐对象记账——遵守 §4.20 的原则：逐对象记完成清单，在十亿级对象下写放大量不可接受。
4. journal 是只追加的文本文件；**任何出错或竞态的后果都只是"重复劳动"，不允许出现"有对象漏掉没人检查"**。

**非目标**：

- 不接 Mode 1 / Mode 3（本期只做 Mode 2；它们的列举代码结构不同，将来另做）。
- 文件输入模式（-list-file / -check-file / -backup-file）没有 LIST，不适用。
- 不做 fsync：防的是进程被杀，不是整机断电；数据进了操作系统缓存就够（和 P0 的周期 flush 同一个口径）。
- 不做 journal 压缩：一整轮约几百 MB，重放只要几秒，真需要时再加。
- 不改优雅停机路径（drainQueuedPrefixes / list_failed.txt / -resume-list 全部保持原样）。

**做错就算失败的点**：

- journal 说某页已完成，而该页对象的结果行其实没写进文件 → 恢复时跳过它们 → 有对象永远没被检查。
- 探测主路径的性能回退（每个对象新增的操作必须是常数且微小）。

## 3. journal 文件：记什么

位置：`<output_dir>/journal.txt`（和 run.log 同级，每次运行自己的时间戳目录里）。只追加，每行一个事件，共三种：

```
discovered|<prefix>          发现了一个新的子前缀
cursor|<prefix>|<token>      这个前缀推进到了 token 位置
done|<prefix>                这个前缀全部完成
```

**"完成"的准确定义（全文最重要的定义）**：某前缀的一页算完成，当且仅当这页的全部对象都**探测结束，且结果行已经写进了输出文件**。不是"列举过了"，不是"发出去了"，是"结果在盘上"。

**cursor 行的含义**：该前缀从头到 token 的所有页都满足上面的完成定义；token 是"下一页从哪继续列举"的凭证（S3 分页的 continuation token）。语义和 list_failed.txt 里的 token 一致。

**重放规则**：从头到尾扫一遍，每个前缀只看它的最后一条事件。只有 discovered、没有 cursor/done = 发现了但还没开始。

**为什么 cursor 记"结果已落盘的位置"，不记"LIST 请求翻到哪了"**：lister 的列举进度永远跑在探测进度前面（objCh 通道容量约 2000 个对象，满了 lister 就停下来等）。假设 LIST 翻到第 100 页、探测只完成到第 98 页：

- 若 journal 记第 100 页：恢复从第 101 页继续，第 98~100 页里"已列出但还没探测"的对象永远没人查 → 漏了；
- 若 journal 记第 98 页：恢复从第 98 页的 token 继续，重列重探 98~100 页 → 多干活，但不漏。

所以记后者。全文反复出现的"只多干活、不漏对象"，出处就是这里。

**前缀名里可能带 `|`**（现在的代码对这种前缀照常入队列举，只有对象名带 `|` 才落 invalid_keys）。journal 的解析因此不能从左往右切：

- discovered / done 行：前缀 = 去掉第一个字段后的整行剩余（原样保留，带 `|` 也不歧义）；
- cursor 行：token 永不含 `|`（S3 协议保证：V2 是 base64，V1 是 key），所以按**最后一个 `|`** 切开；
- 对比：list_failed.txt 从左切分，表示不了带 `|` 的前缀（既有局限，不改）；journal 文法能表示——为了不漏对象。

空 / 根前缀写成空字段（`discovered|`、`cursor||token`），能和现有的 `prefix\x00token` seed 机制对接。重放时末行没有换行符（进程死在写了一半）就丢弃——少记一点、恢复多干一点，安全。

## 4. 运行时：怎么记账

一个 journal tracker（一个带锁的小结构），三个记账入口。

**lister 侧**：

- `ListPage` 成功返回时：登记"这页一共有 N 个对象"（N = len(objs)，**一次性登记，之后不变**），并记下这页的 next token；
- 发现新的子前缀时：登记 discovered。**必须发生在这页对象进入 objCh 之前**——现在的 processPrefix 把子前缀入队放在对象循环之后，要调整顺序。否则可能出现"这页对象都探测完了、这页发现的子前缀还没记账"的中间状态：如果 checkpoint 恰好在这时发生，那个子前缀就永久丢了；
- 一页里有些对象根本不进通道（对象名带 `|` 直接落 invalid_keys 等）：登记页计数时直接扣除；
- 一页翻完（next 为空）：记一个"翻页结束"标记。

**checker 侧**：

- `Handle` 返回时（结果行已经推进了输出通道）：对（前缀, 页号）记一次"完成 1 个"。没有输出行的对象（如 is_success_log 关闭时的干净对象）也照样记——探测结束本身就是完成；
- 每个对象在热路径上就这一次加锁计数。

**list-only 模式**（is_check=false）：没有 checker，lister 本地分类完就是终态，"完成位置"和 LIST 位置重合。

**页完成判定**：某页的完成计数累计到 N → 这页完成。前缀的完成位置 = 连续完成的最后一页；全部页完成且翻页结束 → done。

**一条关键规则（半页打断的正确性来源）**：页计数 N 是 ListPage 返回时登记的整页数量，**不随实际推送了多少个而变化**。硬停（第二次信号）打断在半页时：已进通道的对象快速失败、各记一次完成，但没进通道的对象永远不会有完成记录 → 这页计数永远到不了 N → 完成位置冻在这页之前 → 恢复时重列整页。举例：一页 1000 个对象，推到第 400 个被硬停——错误的记法（记 400）会让这页"假完成"，第 401~1000 个对象从此没人查；正确的记法（记 1000）让这页永远差 600 个，恢复时整页重来。**宁可重列，不可漏过。**

**内存控制**：已经写进 journal 的状态，从内存 map 里删掉（journal 文件是完整状态的权威来源，重放"取最后一条"本来就容忍重复行）。内存里只留：本周期新产生的 + 还在处理中的。这样内存量级是"十分钟的工作量"，而不是"整个桶的前缀数"——千万级前缀全放内存就是 GB 级，本设计防的就是长跑 OOM，不能自己造一个。

## 5. checkpoint：什么时候写、按什么顺序写

一个独立 goroutine，每 10 分钟执行一次（常量；包级变量，测试可改小到毫秒级）。**顺序固定三步**：

```
第 1 步：给 tracker 拍快照（加锁读出：本周期新发现的、各进行中前缀的完成位置）
第 2 步：把输出文件刷到盘（FlushAndWait，含义见下）
第 3 步：把快照写进 journal：discovered 行在前，cursor/done 行在后
```

**第 2 步的准确含义**："开始刷之前已经推进输出通道的每一行，都写进了文件"。这不只是把 64KB 缓冲刷出去——通道里可能还积着最多 1024 行（还没被 writer goroutine 取走），只刷缓冲会漏掉它们。实现用一个**标记值**：往每条输出通道里推一个特殊值，它像普通行一样排队前进；writer goroutine 看到它，就知道前面的行都处理完了 → 刷缓冲 → 回报完成。9 条 .txt 输出通道都要覆盖（包括 invalid_keys 那条——lister 的短路对象是"立即完成"的，结果行同样要落盘）。.log 文件逐条直写、天然在盘上，不用管。

**为什么是"先快照、再刷盘、最后写 journal"**：

- 完成计数是"结果行推进通道**之后**"才记的 → 快照里看到的每个完成，其结果行的推进时刻必然早于快照时刻 → 早于刷盘时刻 → 刷盘必然覆盖它；
- 反过来（先刷盘再快照）：刷盘和快照之间新推进的行没落盘，但完成计数已进了快照 → journal 声称完成、行不在盘上 → 漏。

**同一批内 discovered 行写在 cursor/done 之前**：进程死在批次中间时，最多出现"子前缀已 discovered、父前缀没 done"（恢复时重列父前缀、重新发现，安全），绝不会出现"父前缀 done、它下面的子前缀没 discovered"（那个子目录就蒸发了）。

## 6. 出错时的后果清单（验收标准）

每种错误/竞态，后果必须是"多干活"，不允许是"漏对象"：

| 情形 | 后果 |
|---|---|
| checkpoint 间隔内的进度（最多 10 分钟工作量） | 恢复时重做 |
| 进程死在快照之后、写 journal 之前 | journal 少记一截，恢复时重做 |
| 进程死在刷输出与写 journal 之间 | 同上 |
| 硬停打断在半页 + checkpoint 在其后触发 | 页计数不归零、完成位置冻结，恢复时重列整页 |
| journal 里有重复/乱序行 | 重放取最后一条，幂等 |
| journal 末尾有残行（无换行符） | 丢弃，恢复时重做 |

## 7. 恢复：-resume-journal

```
./chunked_check_tool -c cfg.yaml -bkt <bucket> -resume-journal <被kill那轮的目录>/journal.txt
```

- 只支持 list_type=2（校验方式和 -resume-list 一致，其他值报错）；
- 与其他文件类 flag 互斥；
- **-prefix 必须为空**（journal 本身就定义了扫描范围，防止范围对不上），非空报错；
- 恢复过程：重放 journal（几秒）→ 有 cursor 的前缀用现有 SeedWithToken（`prefix\x00token`）进 BFS 队列；只 discovered 没动过的当裸前缀入队；done 的不碰。**从根重新列举一次都不需要**——目录树全在 discovered 行里；
- journal 为空或没有 discovered 行（进程死在第一次 checkpoint 之前）→ 等于普通全量重跑，退回现状行为；
- 恢复轮自己也开始记 journal（写到它的新时间戳目录），可以再次被 kill、再次恢复；
- **journal 对所有 Mode 2 的 S3 列举运行生效**：全新扫描、-resume-list 恢复轮、-resume-journal 恢复轮都记账。理由：-resume-list 轮也是长跑，不记账的话它被 kill 又是全损；
- 输出的跨轮合并语义不变（union + sort -u），收敛判据不变（最新一轮失败文件为空）。

## 8. 与现有机制的关系

- list_failed.txt 照写（S3 LIST 报错的通道不变）。journal 的完成位置永远 ≤ 失败页的位置，-resume-journal 恢复时自然会重试失败页，两者不打架。
- 优雅停机后的恢复用 -resume-list 更精确（list_failed 里是停机瞬间的现场）；用 -resume-journal 也可以（journal 落后最多一个周期，多重做一点）。两个入口并存，各服务各场景。
- -resume-list 本身一行代码不改。

## 9. 我做的取舍（可驳回）

1. checkpoint 间隔 = 常量 10 分钟（包级变量，测试可改小），不进 config——内部细节，沿 outputFlushInterval 先例。
2. 文件名 journal.txt，放输出目录根。
3. flag 名 -resume-journal；和 -prefix 一起用就报错。
4. 不做 fsync（只防进程被杀，不防断电）。
5. 优雅停机路径一行不动。
6. list-only 模式（is_check=false）也记账。
7. journal 不记录 S3 LIST 报错（那是 list_failed.txt 的职责）。
8. 带 `|` 的前缀照常入队列举（扫描行为不变），journal 文法容忍它们（§3）。
9. 已写盘的状态从内存删除，journal 文件是权威全量（§4 内存控制）。
10. 所有 Mode 2 S3 列举运行都记账，包括 -resume-list 恢复轮（§7）。

## 10. 留给实现计划的事

- FlushAndWait 的标记值机制具体实现（9 条通道各一个，per-owner fan-out 也要覆盖）。
- 页号 / token 的内部数据结构（每个进行中的前缀一个小 map 或环形缓冲）。
- VerifyTask 加字段（前缀 + 页号）——涉及多文件接口改动，按 AGENTS §9 先记 ledger。页号只在进程内用，不写进 journal（token 才是持久化的游标）。
- processPrefix 调整顺序：发现子前缀的记账移到这页对象进通道之前。
- checkpoint goroutine 的接线；运行开始时把根前缀记一条 discovered。
- 重放器（§3 解析规则）+ seed 接线 + main 的 flag 校验。
- 测试清单：
  - 完成位置的推进逻辑；
  - 半页打断 + 之后触发 checkpoint → 完成位置必须冻结（本设计最关键的正确性测试）；
  - "完成计数在结果行推进通道之后"的顺序约定；
  - 批内行序（discovered 在前）；
  - 带 `|` 前缀的 journal 读写往返；
  - 模拟 kill：跑到一半不调 Close 直接重放 journal，断言状态正确；
  - -resume-list 轮被 kill 后用 -resume-journal 恢复的端到端测试。
- AGENTS.md 更新：§4.20（kill -9 从"有损"改为"journal 兜底"）、§5 flags 表、§6 输出文件表加 journal.txt、新增 §7.5 冒烟 runbook。

## 11. 规模与风险

- 规模：约 500-800 行新代码 + 测试。新文件 journal.go；改动 main.go、lister.go、checker.go + VerifyTask、output.go（加 FlushAndWait）。
- 最大风险：记账与 checkpoint 顺序的并发正确性。对策：§6 表格作为 review 和测试的验收标准，每一行都要有测试钉住。
- 性能：热路径每对象多一次加锁计数（纳秒级）；journal 写入每 10 分钟一批顺序追加。对 5000 IOPS 的探测流量无可感知影响。
