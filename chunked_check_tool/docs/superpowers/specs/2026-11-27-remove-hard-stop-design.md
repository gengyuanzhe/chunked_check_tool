# 删除两段式信号的硬停 — 设计

日期: 2026-11-27
状态: 已批准并实现（用户确认："接受，删除硬停"）

> 后续变更（同日）：本文保留的"第一次信号：停止列举并排空"也已被删除，进程不再拦截任何信号。见 `2026-11-27-remove-signal-handling-design.md`。本文其余内容保留作当时的记录。

## 1. 背景

进程原来按"两段"响应 Ctrl-C / kill：

- 第一次信号：停止列举和读输入，把已经发出去的任务做完（下称"排空"）。
- 第二次信号：立即中止正在进行的检查和中转，把排队中的任务记进失败文件（下称"硬停"）。

硬停存在的理由是"让突然停下来也有办法补跑"。这个理由现在不成立了：`list_type=2` 的扫描有定期快照（`journal.txt`），`-check-file` 和 `-backup-file` 可以用结果文件求差集。续传能力由这两样保证，不需要靠信号。

硬停自己还有问题：它中止多段中转时做的清理请求发不出去，会在备份桶留下没传完的分片上传。

## 2. 目标与非目标

目标：

- 删掉硬停这条路径，以及只为它存在的参数、分支和测试。
- 第一次信号的行为（排空）完全不变。

非目标：

- 不改 `journal.txt` 的记录方式和恢复入口。
- 不改文件输入模式求差集的做法。

做错就算失败：

- 排空过程中进程被信号杀死，或者留下不完整的 `list_failed.txt`。
- 留下永远不会被取消的上下文参数。

## 3. 方案比较

| 方案 | 做法 | 结论 |
|---|---|---|
| A | 之后的信号不再有动作，想立即停只能 `kill -9` | **采用** |
| B | 第二次信号恢复系统默认行为，直接杀死进程 | 不采用 |
| C | 保留硬停，只修清理请求的 bug | 不采用 |

B 不采用的原因：它等于还留着一条强停路径。进程在排空中途被杀时，`list_failed.txt` 可能只写了一半，操作员拿它去 `-resume-list` 就会漏掉前缀。A 之下要么完整排空，要么由操作员主动 `kill -9`，这时操作员清楚知道要走快照恢复。

C 不采用的原因：和"续传只靠定期快照"的方向相反。

## 4. 设计

### 信号处理

- 收到第一个 SIGINT/SIGTERM：取消 `listCtx`，停止列举和读输入，开始排空。日志提示"要立即停请 kill -9"。
- 之后的信号：不再有动作。信号通道保持注册，后续信号被吞掉，不会杀死进程。

### 代码上删掉什么

- `hardCtx` 整条删除：`run`、`runBackup`、`Lister.Run`、`processPrefix` 的参数。
- 列举器往检查队列送对象时的两处"响应硬停"的分支（列举器和 `list_type=1` 的根分页循环），改回普通发送。
- `Checker` 和 `BackupChecker` 不再持有上下文，检查和中转用 `context.Background()`。单次检查请求的 30 秒超时仍在 `S3Client` 里，不受影响。

`journal.txt` 里"一页算完成"的定义没变：这一页的全部对象都检查完才算。只是注释里不再提硬停。

## 5. 各模式下被 `kill -9` 之后怎么续

| 运行模式 | 续跑办法 | 重做多少 |
|---|---|---|
| `list_type=2` 扫描 | `-resume-journal <被杀那轮目录>/journal.txt` | 最多 10 分钟的进度 |
| `-check-file`、`-backup-file` | 重跑原输入，或用结果文件求差集只跑没定论的对象 | 没处理的部分 |
| `list_type=1` | 用相同参数重跑全量扫描 | 整轮 |

`list_type=1` 的代价用户已接受。

## 6. 代价

- 排空不能被缩短。最坏情况是队列里的任务数乘以单次超时，再除以并发数。
- 备份模式下被 `kill -9`，备份桶会留下没传完的分片上传。这一点原本就有，处理办法见 `AGENTS.md` §7.4。
