# 删除 Ctrl-C 处理（不再拦截信号）— 设计

日期: 2026-11-27
状态: 已批准（用户确认："删除，半截分片的事情不用考虑"）

## 1. 背景

同日的前一步删掉了第二次信号的硬停，保留了第一次信号的处理：收到信号后停止列举，把已经发出去的任务做完（下称"排空"），然后干净退出。

续传能力靠的是 `journal.txt` 定期快照和结果文件，不靠 Ctrl-C。于是排空只剩两个用处：让 `list_type=2` 的快照在退出时补到最新、不用重做；让备份模式正在传的对象传完。用户衡量后决定整个删掉。

## 2. 目标与非目标

目标：

- 删掉所有信号处理，以及只为它存在的参数、分支和测试。
- 删掉之后 Ctrl-C、kill、`kill -9` 效果相同：进程立即退出。

非目标：

- 不改 `journal.txt` 的记录方式、间隔和恢复入口。
- 不改文件输入模式求差集的做法。
- `list_failed.txt` 和 `-resume-list` 保留：它们还用来重试运行中真正失败的页。

做错就算失败：

- 留下任何"接收上下文但永远不会取消它"的参数。
- 文档里还有"收到信号会排空"的说法。

## 3. 方案比较

| 方案 | 做法 | 结论 |
|---|---|---|
| A | 信号处理全部删除 | **采用**（用户的决定） |
| B | 保留排空 | 不采用 |
| C | 收到信号只写一次 journal 检查点，然后立即退出，不排空 | 没有讨论过，见下 |

B 不采用的原因：约 125 行产品代码和一条最容易出错的并发路径，换来的只是停车时少重做几分钟。

C 是写这份文档时想到的折中：十几行代码就能保住"`list_type=2` 停车不重做"这一点。它没有和用户讨论过，本次没有实现。如果之后觉得每次停车最多重做 10 分钟太多，可以考虑。

## 4. 设计

删除的内容：

- 信号处理函数，以及"被中断"的返回值和它的三处判断。
- "收到信号时把还没开始的前缀记进 `list_failed.txt`"的函数，和队列里只为它服务的清空方法。
- 队列等待、文件读取、列举器里所有"上下文取消了就退出"的判断。
- `run`、`runBackup`、`Lister.Run`、`processPrefix`、`fileSource.Run` 的上下文参数。需要上下文的 S3 调用一律传 `context.Background()`。

删除后的行为：

- 进程不执行任何收尾代码：不刷输出缓冲，不写 journal 的最终检查点，不打印汇总。
- 结果文件可能缺最后 3 秒的行（每 3 秒定期刷一次盘），末行可能是半行。

## 5. 代价

用户已接受：

- `list_type=2` 每次被杀最多重做一个快照间隔，默认 10 分钟。
- 备份桶里留下没传完的分片上传。用户明确表示不用考虑。

需要知道的：

- LIST 请求本身没有单次超时。服务端接受连接后一直不回应时，工具会一直等着，只能靠 kill 停掉；可以配置 `response_header_timeout` 兜底。

## 6. 验证

- 先改测试再改实现：调用点改成新签名，编译失败确认后才改实现。
- `drain_test.go` 整个文件删除（它测的都是信号和排空），文件读取的"取消"测试删除。查看队列内容的两个测试改用测试文件里的小辅助函数。
- 端到端（2026-11-27 实跑）：起一个只接受连接、永不应答的服务器，让工具卡在列举上，发 SIGINT。结果：进程 0 秒退出，退出码 -2（被信号杀死），`run.log` 里没有汇总，也没有信号日志。
- 全量测试带 `-race` 通过。
- `AGENTS.md` §7.3 的冒烟步骤改写成了"LIST 失败后的 `-resume-list` 闭环"，改写后没有重新实跑。
